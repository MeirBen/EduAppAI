What do the run statuses mean?

Completed means the workflow finished, not that every check passed. Rate-limited, cancelled and failed runs may contain useful partial results. Inspect the report before starting another run: there are no automatic retries, and a new run starts from the beginning.

Run evaluation

New here? A practical workflow
  1. Start with one relevant case and one repeat. Leave the Hebrew judge off for a basic generation check.
  2. Review the call estimate, set a sufficient Max calls limit, and confirm the run.
  3. Open the report in History. Read the generated content and answers, then record your human review.
  4. Enable the Hebrew judge when investigating language quality. It adds advisory feedback and extra calls.
  5. Label a baseline, change one prompt or model setting, and run the same selection again before comparing.
Evaluation cases

Each selected case tests a parent request through AI template creation and then task generation. The focus text describes what you should review; it is not an automatic quality score. Start small before selecting the whole suite.

Where do these cases come from?

They are maintained synthetic examples in cases.json, not your family's saved content. Add a case for a real usage gap or regression; keep its expectations aligned with the request. Restart the dashboard after editing. Task generation uses the generated defaults, or the count maximum when a case requests it; these runs do not exercise every possible field value.

Each repeat creates a fresh template and task. Use repeats to observe variation; they do not reuse the same generated template.

Max calls must cover the whole plan; it is not a currency or token limit. The estimate is an upper bound: failed stages can skip later calls. Provider fallback attempts may add cost. Use an OpenRouter key spending limit for a monetary cap.

Adds AI proofreading of the generated template and task using the same AI configuration, including any fallback. It reports language findings and suggested corrections; it never rewrites content, fixes answers or assigns the human scores.

How the Hebrew judge works — and when to use it
  1. Calibration first: known examples test whether the judge catches specific errors and avoids flagging acceptable text. These calls run once per run, not once per repeat.
  2. Content review next: each successful template/task pair gets one review for spelling, invented words, agreement, sentence structure, idiom and unintended language mixing.
  3. You decide: inspect the quoted field, suggestion and explanation. The same model can miss its own mistakes. Passing calibration or reporting no findings is not proof of good Hebrew or correct teaching content.

Use it when comparing language quality or investigating a Hebrew regression. Keep it off for quicker, lower-call checks of generation and structure. Human review remains available either way.

Labels and notes help you recognize experiments later. They are saved with the report and do not change the AI request or comparison rules.

What do these settings control?
Model / fallback
The requested model and optional provider-error fallback. A fallback is not a second independent judge.
Response format
How JSON is requested. The app validates every response; valid JSON does not guarantee correct content.
Reasoning
Optional thinking controls. Reasoning uses time and the output-token allowance, even when its text is not displayed.
Temperature / top-p / top-k
Sampling controls. Support varies by endpoint; no value guarantees fluent Hebrew. Unset controls use provider defaults.
Tokens / timeout
Output and time ceilings. Reaching a ceiling can prevent a complete response. These limits are not quality targets.

How to read a report
Contract passed
The response met the app's structure and validation rules. Read the content to assess language and correctness.
Automatic checks
Case-specific checks such as question count, choice count, interaction type and passage length. A pass does not cover every instruction in the request.
Judge calibration
Detection of known errors and false alarms on fixed examples. Failed or unfinished calibration weakens confidence in the judge; content reviews can still run.
Hebrew findings
Advisory language defects from the AI reviewer, separate from automatic checks and your scores. No completed review means no language evidence, not zero errors.
Human review
Your assessment of the actual output. Score 0 for unusable, 1 for needs edits, 2 for ready; leave a dimension unreviewed when you have not checked it. Record examples in the notes.
Cost / latency
Reported cost can be incomplete; unknown does not mean free. Average latency covers returned responses, including rejected content, but excludes timeouts and transport failures.

Raw request/output sections help investigate a failure. Reports contain generated answer keys; keep them private. Saving a human review changes only the local scores and notes, makes no AI call and does not fix the generated content.

Compare saved runs

Descriptive changes only. Deltas mean candidate minus baseline; there is no combined score or winner.

How to make a useful comparison
  1. Choose an earlier reference run as the baseline and the experiment as the candidate. Change one model or prompt setting at a time.
  2. Keep the case suite, selected cases, repeats and judge setup the same. Incomplete runs or changed fixtures can make the runs incomparable.
  3. Read compatibility first. Hebrew finding deltas also require passing calibration and matching reviewed results; human-score deltas need the same scored results.
  4. A positive delta only means the candidate value is higher: more passes may help, more failures or findings may hurt. Inspect the examples before drawing a quality conclusion.

Unknown measurements stay unknown. Comparing reports is offline and free of AI calls; it never chooses a winner or updates your model settings.
